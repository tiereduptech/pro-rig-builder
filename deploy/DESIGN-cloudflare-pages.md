## 1. Scope

This replaces `server.cjs` — the Express app Railway runs — with static assets
on Cloudflare Pages plus one Pages Function.

It does **not** replace the Epik stack. Epik and Pages are two independent
targets fed from the same committed `dist/`, and they stay that way through the
migration so either can serve production. The pieces that decide behaviour —
`PRODUCT_RE`, `product-redirects.json`, the 410 shell transform — are shared by
construction rather than reimplemented per stack; see §3.

| | Railway (today) | Epik | Pages |
|---|---|---|---|
| static assets | `express.static` | Apache/LiteSpeed | Pages edge |
| 301/410 resolver | `server.cjs` L4.5 | `deploy/resolver.php` | `functions/parts/[[path]].js` |
| SPA fallback | `server.cjs` L5 | `resolver.php` tail | same Function |
| product boundary | `PRODUCT_RE` literal | `resolver-config.php` | `resolver-data.generated.js` |
| per-product JSON | same origin | same origin | `data.prorigbuilder.com` (R2) |
| build artifacts | — | `build-epik.cjs` | `build-pages.cjs` |

## 2. Topology

```
                          prorigbuilder.com
                                 │
                    ┌────────────┴─────────────┐
                    │   Cloudflare Pages edge   │
                    └────────────┬─────────────┘
             /parts/*            │            everything else
                    │            │                    │
   functions/parts/[[path]].js   │            static assets
   (Worker, ~5.5k product pages  │            (prerendered HTML,
    + the 301/410/SPA decision)  │             hashed /assets/*)
                    │            │
                    └── next() ──┘
                                 │
   price charts / reviews  ──────┴──────►  data.prorigbuilder.com  (R2)
   fetched by the browser, not by the edge      [workstream 3, live]
```

`_routes.json` is generated by wrangler from the `functions/` tree and comes out
as `{"include": ["/parts/*"], "exclude": []}` — verified, §5. Every request
outside `/parts/` is served with no Worker in the path at all.

## 3. The resolver, and the invariant that keeps three stacks honest

`functions/parts/[[path]].js` implements exactly what `server.cjs` Layers 4.5
and 5 implement, and what `deploy/resolver.php` implements for Epik:

| request | answer |
|---|---|
| asset exists | serve it |
| product-shaped, in the redirect map | `301` + relative `Location` |
| product-shaped, not mapped | `410` + `X-Robots-Tag: noindex` + noindex shell |
| anything else | SPA shell at `200` |

"Product-shaped" is `PRODUCT_RE`, and it is the load-bearing decision: it is what
separates "this URL is gone, de-index it" from "this is a client-side route,
serve the app". Get it wrong in one direction and live category pages start
returning 410; wrong in the other and the entire retired catalog soft-404s. Both
failures are silent — the deploy is green and the only symptom is organic
traffic weeks later.

So it is never retyped. `server.cjs` holds the single literal; `build-epik.cjs`
extracts it into `resolver-config.php` and `build-pages.cjs` extracts it into
`resolver-data.generated.js`, both with the same regex against the same line.
`build-pages.cjs` additionally runs an eight-case truth table over the extracted
copy (product, trailing-slash product, category index, browse pagination,
deeper-than-product, slug without an id, non-`/parts/` route) and refuses to
build if any case moved. A change to `PRODUCT_RE` in `server.cjs` therefore
fails the Pages build loudly instead of quietly shifting the 410 boundary.

The 410 shell gets the identical transform in all three stacks — strip every
`robots`/`googlebot`/`bingbot` meta, strip the canonical, force one `noindex` —
and `build-pages.cjs` asserts the result contains a noindex, contains no `index`
directive, and carries no canonical before it will emit anything.

## 4. Two platform behaviours that decide the shape of this design

Both measured with `wrangler pages dev` (wrangler 4.86.0, workerd) against the
real `dist/` on 2026-08-15. Both should be re-confirmed on the first staging
deploy; they are local-runtime observations, not documented guarantees.

### 4.1 Without a `404.html`, the resolver is dead code

Cloudflare's asset service has a built-in single-page-application fallback: a
request matching no asset, in a tree with no `404.html`, is answered with the
**root `index.html` at status 200**.

The Function decides "was this URL real?" from the status of its `next()` call.
Under that default `next()` returns 200 for a deleted product exactly as it does
for a live one, the `!== 404` test short-circuits, and every branch past it —
301, 410, SPA fallback — is unreachable. Observed directly: `RESOLVER-NEXT
status=200` on a path with nothing behind it.

The failure is invisible from outside. The Function runs, the deploy is green,
the page renders "Product Not Found" for humans, and the whole retired catalog
soft-404s at 200 to crawlers.

`build-pages.cjs` writes `dist/404.html` to restore a real 404 from the asset
service. It gets the **410 shell's** transform rather than being a copy of
`index.html`, for the same reason the 410 shell does: a 404 response carrying
`robots: index` and `canonical: https://prorigbuilder.com/` tells a crawler the
dead URL is the homepage.

**Consequence outside `/parts/`, stated because it is a real behaviour change:**
an unknown non-`/parts/` path now answers 404 where `server.cjs` Layer 5 answered
200-with-the-shell. Checked against `public/sitemap.xml` — all 26 non-`/parts/`
entries are prerendered, so no indexable URL moves. Humans still get a booting
app shell; only the status differs, and a hard 404 on a genuinely unknown path is
the better of the two answers.

A `/* /index.html 200` rule in `_redirects` reintroduces this exact defect by
another route, which is why `_redirects` is generated empty and says so.

### 4.2 Trailing slash: every canonical URL would 308

Prerendered pages live at `<path>/index.html`. Cloudflare's asset service answers
a request for `<path>` with a **308 to `<path>/`**. Express serves it at 200 and
never redirects.

That difference lands on every URL the site publishes. `public/sitemap.xml` lists
5,519 URLs and exactly one — the root — ends in a slash. Every prerendered
`<link rel="canonical">` is likewise the unslashed form. So on a stock Pages
deploy, every canonical URL 308s to a variant whose own canonical tag points back
at the URL just redirected away from. Search Console reads that as "Page with
redirect" across the entire sitemap, mid-migration.

Cloudflare exposes no control for it. `html_handling` (`drop-trailing-slash`)
belongs to Workers static assets, not Pages: wrangler rejects an `[assets]` block
in a Pages project with *"the `assets` property in your configuration is missing
the required `directory` property"*.

Two fixes, each used where it is the cheap one:

- **Inside `/parts/` (5,493 URLs) — code.** The Function intercepts the redirect
  and returns the slashed asset's body under the requested URL at 200. Scoped to
  exactly the "add a trailing slash" case; any other redirect the asset service
  produces passes through untouched. Costs nothing: a Worker already runs there.
- **Outside `/parts/` (25 URLs) — files.** The asset service resolves `<path>`
  from a sibling `<path>.html` before it considers `<path>/index.html`, and
  serves it at 200 with no redirect. `build-pages.cjs` writes those siblings.
  Costs 25 files.

The same file trick inside `/parts/` would cost 5,484 extra files and ~440 MB per
deploy and push the deployment back toward the 20,000-file ceiling that moving
the data directories to R2 just bought headroom against. Widening the Function
outside `/parts/` would mean a root `_middleware.js`, putting a Worker in front of
every asset on the site to repair 25 URLs. Hence the split.

Both forms answer 200 with identical bytes afterwards — verified.

## 5. Why the Function is scoped to `/parts/`

A catch-all at `functions/parts/[[path]].js` makes wrangler emit
`_routes.json` with `include: ["/parts/*"]`, so only `/parts/` requests invoke the
Worker.

It does mean all ~5,484 prerendered product pages invoke it, because "does this
URL exist" is not answerable from a route pattern — the miss case is defined by
absence. The work on that path is one `next()` and a status check. `_routes.json`
cannot exclude the hits: its `exclude` list caps at 100 rules against 5,484 pages.

The alternative, a root `_middleware.js`, answers the same question while putting
a Worker in front of every asset on every request. Strictly worse.

## 6. Caching

Cloudflare already sends `public, max-age=0, must-revalidate` on every asset,
which is what `server.cjs` Layers 1–3 want for prerendered HTML. Nothing to add.

For `/assets/*` we want something different — hashed, content-addressed output
that `server.cjs` Layer 4 marks immutable for a year — and **`_headers` cannot
express it**. `_headers` appends to what Cloudflare already sent rather than
replacing it, producing:

```
Cache-Control: public, max-age=0, must-revalidate, public, max-age=31536000, immutable
```

The first `max-age` wins. The rule looks applied and does nothing, so
`build-pages.cjs` does not write it — an inert rule reads as "handled" and is
worse than an absence with a reason attached.

The working lever is a **zone-level Cache Rule on `/assets/*`**, available once
the custom domain is attached. Until then hashed assets revalidate; they still
hit the edge cache, so the cost is a conditional request and a 304, not a
re-download. This is a performance item, not a correctness or SEO one.

Note `X-Robots-Tag` is unaffected — Cloudflare sets no such header, so the
staging guard in §7 appends cleanly and does work.

## 7. Staging guard — and its honest weakness

On Epik, staging is guarded by Basic Auth **first** and noindex second, and the
ordering is deliberate: a leaked Basic Auth 401s loudly and is caught in minutes,
whereas a leaked noindex de-indexes silently (the 2026-07-27 incident).

Pages has no equivalent. Basic Auth would need a second Function on every route,
and this stack cannot borrow the `.htpasswd` mechanism. **The Pages staging guard
is the silent-failing layer alone** — `X-Robots-Tag: noindex, nofollow` on `/*`,
appended under `--staging` between `PRB-PAGES-STAGING-GUARD` sentinels.

That is a real weakening relative to Epik, and it is why the check is a hard
refusal in both directions rather than a warning. `build-pages.cjs` writes
`_headers` and then asserts against **what is on disk**, not against the array it
just built:

- production carrying the sentinel or any blanket noindex → refuse to build
- staging *missing* it → refuse to build (a fully crawlable copy of the catalog
  on a `pages.dev` hostname is the same failure from the other side)

Partial mitigation that already exists: every prerendered canonical is absolute
and points at `prorigbuilder.com`, so a preview deployment's pages disclaim
themselves even without the header.

## 8. Deploy pipeline

`.github/workflows/deploy-pages.yml`, workstream 4. Dispatch only — no push
trigger — with the same `if:` shape as `publish-epik.yml` and `deploy-epik.yml`
so the gate is already correct when a push trigger is added at cutover.

It ships the **committed** `dist/`, exactly as `deploy-epik.yml` does. The
45-minute prerender never runs in the deploy path.

One consequence is worth stating because it surprises people: **the deploy
workflow cannot change what is in the JS bundle.** The prerendered HTML
references `dist/assets/*.js` by content hash, so re-running `vite build` in the
deploy path emits hashes that none of the 5,568 committed HTML files point at —
a site that loads a blank shell. `VITE_DATA_BASE` must therefore be set where the
bundle is *built*, in `prerender.yml`, not in the deploy workflow. The workflow
detects which way the committed bundle was built and adapts the upload rather
than assuming.

### 8.1 Required configuration

| kind | name | value |
|---|---|---|
| secret | `CLOUDFLARE_API_TOKEN` | Account → Cloudflare Pages → **Edit**, scoped to the account. Not the R2 S3 keys. |
| secret | `CLOUDFLARE_ACCOUNT_ID` | already set; shared with `sync-data-r2.yml` |
| var | `CF_PAGES_PROJECT` | the Pages project name |
| var | `VITE_DATA_BASE` | `https://data.prorigbuilder.com` — also set it on `prerender.yml` |
| var | `CF_PAGES_AUTO_DEPLOY` | unset during migration; `true` at cutover |

### 8.2 Creating the project

It must be a **Direct Upload** project. Creating it through the dashboard's
"Connect to Git" flow wires Cloudflare's own build system to the repo, which
would deploy on push and rebuild independently of Actions — both of which this
design deliberately does not do. A project is one kind or the other for life;
it cannot be converted.

```
wrangler pages project create <name> \
  --production-branch=main \
  --compatibility-date=2026-05-01
```

`--production-branch` must be `main`: the deploy workflow passes `--branch=main`
for `target=production` and `--branch=staging` for `target=staging`, and
Cloudflare decides production-vs-preview by matching that against this setting.

The compatibility date belongs on the project because `wrangler pages deploy`
has no `--compatibility-date` flag, and the Pages config file cannot supply one
here either — `wrangler.toml` needs `pages_build_output_dir`, which conflicts
with the workflow deploying an assembled directory outside the repo.

## 9. First-deploy verification

Deploy `target=staging` and check, against the preview URL:

1. `curl -I <preview>/parts/ram` → **200**, not 308 (§4.2)
2. a live product URL, no trailing slash → **200**, and its body carries the real
   `<link rel="canonical">`, not the shell
3. a mapped retired URL → **301**, `X-PreRender: gone-301`, relative `Location`
4. an invented product URL → **410**, `X-Robots-Tag: noindex` (§4.1 — if this is
   200, `404.html` did not ship and the resolver is inert)
5. `/parts/nosuchcategory` and `/parts/ram/browse/page-2` → **200**,
   `X-PreRender: spa-fallback`
6. any unknown non-`/parts/` path → **404**
7. every response carries `X-Robots-Tag: noindex, nofollow` (§7)
8. the run log shows wrangler uploading a Functions bundle — if it says
   `No Functions`, `functions/` was not picked up and items 3–5 will all be wrong

## 10. Open items

- **Zone Cache Rule for `/assets/*`** (§6) — after the custom domain is attached.
- **`VITE_DATA_BASE` in `prerender.yml`** — until the nightly rebuilds `dist/`
  with it, the committed bundle still fetches per-product JSON same-origin and
  the deploy ships the ~10.8k data files. Not broken, just not the end state.
- **Re-confirm §4.1 and §4.2 on the first staging deploy.** Both are local
  `wrangler pages dev` observations. The fixes are harmless if the production
  edge turns out to behave differently — a `404.html` that is never served, and
  sibling files that are never reached — but the *reasons* would need revisiting.
- **Basic Auth for staging** (§7) — only if the noindex-only guard proves
  insufficient.
